# DSH GitHub PR 自动评审

本仓库接入 DeepSeek Harness（DSH）的 PR 自动评审：当 PR 从 draft 变为
**Ready for review** 时，DSH 会在本地仓库工作区创建一个评审会话，把可执行的正确性、
安全与测试发现写在会话里。

> 这套链路的实际配置位于运行它的那台机器上（DSH profile 的用户 patch 层与本地插件目录），
> **不在本仓库内**，因此本文件是行为说明，不是可复现的部署文档。

## 触发条件

规则只接受：本仓库的、事件 `pull_request`、动作 `ready_for_review`。

因此下列情况**不会**触发评审，需要手动兜底：

| 情况 | 事件动作 | 说明 |
|---|---|---|
| PR 创建时已是 ready（非 draft） | `opened` | 不会评审 |
| PR 被 reopen | `reopened` | 不会评审 |
| 已 ready 后又推了新提交 | `synchronize` | 不会评审，已评审的 PR 会偏离当初捕获的 head SHA |

**手动兜底**：把 PR 切换为 draft，再切回 Ready for review，即可重新触发一次。

## 会话里会发生什么

- 会话标题形如 `Review <owner>/<repo>#<编号>`；
- 被捕获的精确 head SHA 出现在**会话的任务文本**里，而不是标题里；
- 会话被要求先重新拉取实时 PR 元数据，而不是只信 webhook 快照——注意这只是对会话的
  指令，harness 本身只传递 webhook 快照；
- 会话被要求不改动文件、分支、PR 或 GitHub 状态。

## 怎么确认评审真的发生了

**不要用 webhook 的 HTTP 202 作为判据。** 该端点是「签名与 JSON 已被接受」就回 202，
并不等待规则结算。实测被规则忽略的投递同样得到 202：

| 投递 | 结果 |
|---|---|
| `ping`、`pull_request/opened`、`pull_request/synchronize`、`converted_to_draft` | 202，**未创建会话** |
| `pull_request/ready_for_review` | 202，**创建了评审会话** |

真正的判据是**出现了一个评审会话**：在 DSH 侧栏里看到标题为
`Review <owner>/<repo>#<编号>` 的会话，或在 DSH 主目录的会话目录下出现对应的新会话。

## 安全边界（准确版）

评审会话会读取**不可信的 PR 内容**，所以写权限是被刻意收紧的——但**不是「绝对只读」**：

- 提供给会话的 GitHub 工具面被限制为只读操作：创建分支、推文件、合并 PR 等写工具不会下发；
- 会话以只读权限预设运行。

**这一保护只覆盖工具面这一层。** 会话本身仍有 shell，而运行它的机器上安装并授权了
GitHub CLI，其令牌具备仓库写权限，因此 shell 里的 CLI 可以绕过工具面直接写入。
换句话说：**「自动评审不改动任何东西」是配置目标与提示词要求，而不是不可绕过的强保证。**

需要真正的写权限隔离时，应给该场景配置只读令牌，或限制评审会话的 shell 工具。

## 已知限制

- 评审只覆盖触发那一刻的 head SHA；之后的新提交需要重新触发。标题不含 SHA，
  判断「评审的是哪个提交」需要看会话内文。
- 评审结论由模型给出，可能误报或漏报，仍需人工判断。
